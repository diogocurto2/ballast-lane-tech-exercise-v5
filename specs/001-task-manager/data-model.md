# Data Model: Personal Task Manager (001-task-manager)

**Phase**: 1 - Design | **Date**: 2026-11-16 | **Plan**: [plan.md](./plan.md) | **Spec**: [spec.md](./spec.md)

Two entities, matching the specification's Key Entities section. Concrete types, constraints, and
migrations are recorded here because the specification deliberately deferred them to planning.

## User

Represents a person who registers and authenticates. Owns zero or more tasks.

| Attribute | Domain type | PostgreSQL type | Nullability | Constraint |
|---|---|---|---|---|
| `id` | `Guid` (`UserId`) | `uuid` | NOT NULL | primary key; generated by the application |
| `email` | `string` (`Email`) | `text` | NOT NULL | unique index on `lower(email)` |
| `passwordHash` | `string` | `text` | NOT NULL | never returned by any API; never logged |
| `createdAt` | `DateTimeOffset` | `timestamptz` | NOT NULL | `DEFAULT now()` |

**Rules**

- `email` MUST be non-empty, MUST match a single-`@` address shape, and MUST be at most 320
  characters. It is normalized to lower case before hashing decisions and before storage
  (PDC-04).
- `email` uniqueness is enforced by the database, not only by an application check
  (`database-standards.md` 2.5), and the resulting unique violation is translated to `409`.
- The plaintext password never reaches the entity. Only its hash is stored, produced by
  `PasswordHasher<User>`.
- No API response contains `passwordHash`. `UserResponse` exposes `id`, `email`, and `createdAt` only.

**State transitions**: none. Accounts are created, never edited or deleted within this scope.

## Task

A personal work item belonging to exactly one user.

| Attribute | Domain type | PostgreSQL type | Nullability | Constraint |
|---|---|---|---|---|
| `id` | `Guid` (`TaskId`) | `uuid` | NOT NULL | primary key; generated by the application |
| `ownerId` | `Guid` (`UserId`) | `uuid` | NOT NULL | `REFERENCES users(id) ON DELETE CASCADE` |
| `title` | `string` | `text` | NOT NULL | `CHECK (length(btrim(title)) BETWEEN 1 AND 200)` |
| `description` | `string?` | `text` | NULL allowed | `CHECK (description IS NULL OR length(description) <= 2000)` |
| `status` | `TaskStatus` | `text` | NOT NULL | `CHECK (status IN ('Pending','InProgress','Completed'))`, `DEFAULT 'Pending'` |
| `dueDate` | `DateOnly` | `date` | NOT NULL | none beyond type; any calendar date is valid, including past dates |
| `createdAt` | `DateTimeOffset` | `timestamptz` | NOT NULL | `DEFAULT now()` |
| `updatedAt` | `DateTimeOffset` | `timestamptz` | NOT NULL | `DEFAULT now()`, set explicitly on update |

**Rules derived from the specification**

| Rule | Source |
|---|---|
| `title` is required and MUST NOT be blank or whitespace only | FR-014, US4.2 |
| `title` length is at most 200 characters | PDC-02 |
| `description` is optional; when present its length is at most 2,000 characters | FR-014, PDC-03 |
| `dueDate` is required, is a calendar date with no time or timezone, and MAY be in the past | FR-014, US4.4 |
| `status` is one of exactly three values | FR-013 |
| A new task defaults to `Pending` | FR-013, US4.1 |
| Status may move between any valid values, in any direction | FR-013, US5.2 |
| `ownerId` is assigned from the authenticated identity and never from client input | FR-009, US4.5 |
| A task belongs to exactly one user; deleting a user cascades to its tasks (not exercised by any endpoint, but declared for integrity) | FR-006, FR-016 |
| Listing is ordered by `due_date` ascending, then `created_at` ascending, then `id` ascending | PDC-05, R16 |

**State transitions**

```text
        create
          |
          v
      [Pending] <---------> [InProgress] <---------> [Completed]
```

Every transition between the three states is permitted in both directions (FR-013). There is no
terminal state and no automatic transition, including for a past due date (PDC-08).

## Relationships

```text
users 1 -------- 0..* tasks
      (owner_id)      ON DELETE CASCADE
```

- A user owns zero or more tasks; a task has exactly one owner.
- Ownership is the authorization boundary: every task query is filtered by `owner_id`
  (`security.md` 2.3).

## Domain value objects

| Type | Purpose | Why not a bare primitive |
|---|---|---|
| `UserId` | Identifies an authenticated user | Prevents mixing user and task identifiers in a query and carries the "validated claim" meaning (`coding-standards.md` 4, primitive obsession) |
| `TaskId` | Identifies a task | Same reason; also keeps signatures self-describing |
| `TaskStatus` | The three-value set | Replaces free text and makes invalid values unrepresentable in code while the database keeps a `CHECK` as the last line of defence |
| `AuthenticatedUser` | The acting identity, built only from validated claims | Makes it impossible to construct an identity from client input (FR-009) |
| `TaskDraft` | A validated create/update payload without an identifier or owner | Makes "ownership is not part of the payload" a type-level fact (FR-009) |

## Table and index inventory

| Object | Definition | Justifying query |
|---|---|---|
| `users` | see above | registration, login lookup by `lower(email)` |
| `users_email_lower_uq` | unique index on `lower(email)` | registration duplicate detection; login lookup |
| `tasks` | see above | all task CRUD |
| `ix_tasks_owner_due_created` | `(owner_id, due_date, created_at)` | `SELECT ... WHERE owner_id = @ownerId ORDER BY due_date, created_at, id` |
| `schema_migrations` | `(version text PRIMARY KEY, applied_at timestamptz NOT NULL)` | apply-once migration runner |

No other index is created. `tasks.id` and `users.id` are covered by their primary keys.
