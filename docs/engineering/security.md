# Security Standard

Authentication, authorization, and data protection rules for this assessment.

## 1. Purpose and scope

This standard defines the security baseline for the APIs, the data layer, and the frontend. It applies to every endpoint, every query, and every configuration file.

The assessment requires user creation, login, authorized and non-authorized endpoints, and storage of user information. This standard makes those requirements concrete and testable.

## 2. Mandatory rules

### 2.1 Credential storage

- Passwords MUST be hashed with an established .NET component: `PasswordHasher<T>` from ASP.NET Core Identity, or a vetted equivalent such as BCrypt. Custom cryptographic algorithms MUST NOT be implemented.
- Plaintext passwords MUST NEVER be stored, logged, returned in a response, or written to an evidence record.
- Each password MUST use a unique salt, generated by the hashing component.
- Hashing parameters MUST be strong enough to be defensible by current guidance and MUST be recorded in the plan.
- Password verification MUST use the component's constant-time comparison, never a manual string comparison.

### 2.2 Authentication

- Login MUST validate credentials against the stored hash and return a token or session credential on success.
- Tokens MUST be validated on every protected request: signature, issuer, audience, and expiry. Validation parameters MUST be explicit rather than permissive defaults.
- Authentication MUST NOT be bypassable by omitting a header, sending an empty token, or sending a malformed token; those cases MUST produce `401`.
- Expired tokens MUST produce `401`, not `403`, and the client MUST be able to detect the condition.
- Token lifetimes MUST be deliberate and documented. A short-lived access credential is preferred for a demo application.
- The signing key MUST come from configuration or a secret store, never a hardcoded literal committed to the repository.

### 2.3 Authorization

- Every endpoint MUST state whether it is public or protected. Public endpoints MUST be marked explicitly (`[AllowAnonymous]` or equivalent), so protection is never lost by omission.
- Protected endpoints MUST require authentication by default, at the point of registration.
- **Resource-level authorization is mandatory.** For every operation on a user-owned record, the application MUST verify that the authenticated identity owns the record.
- User identity MUST be derived from validated claims. Ownership MUST NOT be taken from a client-supplied `userId`, `ownerId`, or similar field in the request body or query string.
- A client-supplied ownership field MUST either be rejected or ignored; the recorded decision MUST be consistent and tested.
- Accessing another user's record MUST return `403` or `404` per a documented, consistent choice. It MUST NOT return the record.
- Administrative or elevated behavior, if any exists, MUST be an explicit role check, not an implicit trust of a client value.

### 2.4 Injection prevention

- All SQL MUST be parameterized. String concatenation or interpolation of values into SQL MUST NEVER be used.
- Identifiers that cannot be parameterized (table or column names) MUST come from a fixed allow-list, never from user input.
- Input MUST be validated server-side before use, including type, length, format, and range.
- Output encoding is a frontend responsibility; the API MUST NOT return pre-escaped HTML as a defense.

### 2.5 Configuration and secrets

- Secrets (signing keys, database passwords, SMTP credentials) MUST come from environment variables, user secrets in development, or a secret store in deployment. They MUST NOT be committed.
- `.env` files and local secret files MUST be git-ignored; an `.env.example` with placeholder values MUST be committed instead.
- `appsettings.json` MUST NOT contain real credentials. Local overrides MUST be git-ignored.
- HTTPS MUST be required outside local development. HTTPS redirection MUST be enabled in deployed environments.
- CORS MUST be an explicit allow-list of known origins. A wildcard origin combined with credentials MUST NOT be used.
- Security headers SHOULD be enabled where the hosting model supports them.

### 2.6 Demonstration credentials

- Seeded demo credentials MUST be clearly labeled as demonstration-only in `README.md`.
- Demo credentials MUST be safe to publish: they MUST NOT grant access to any real system, and MUST NOT be reused from any personal or production account.
- Demo credentials MUST be documented as intentionally public, distinct from real secrets, per [delivery-and-ci.md](./delivery-and-ci.md).

### 2.7 Logging and evidence hygiene

- Logs MUST NOT contain passwords, hashes, tokens, authorization headers, connection strings, or full personal data.
- Request logging MUST exclude credential-bearing bodies and headers.
- GenAI evidence records MUST NOT contain secrets, tokens, or credentials, per [genai.md](./genai.md).
- Error responses MUST NOT reveal whether a username exists in a way that aids account enumeration beyond what a documented product decision requires.

## 3. Practical examples

**Password hashing and verification**

```csharp
var hasher = new PasswordHasher<User>();
var hash = hasher.HashPassword(user, plaintextPassword);   // store hash only
var result = hasher.VerifyHashedPassword(user, user.PasswordHash, suppliedPassword);
if (result == PasswordVerificationResult.Failed) return Unauthorized();
```

**Ownership enforced from claims, not from the body**

```csharp
var ownerId = identity.UserId;                  // from validated claims
var task = await _tasks.FindAsync(taskId, cancellationToken);
if (task is null) return NotFound();
if (task.OwnerId != ownerId) return Forbid();   // resource-level authorization
```

**Parameterized SQL**

```csharp
await using var command = new NpgsqlCommand(
    "SELECT id, title, status FROM tasks WHERE id = @id AND owner_id = @ownerId", connection);
command.Parameters.AddWithValue("id", taskId);
command.Parameters.AddWithValue("ownerId", ownerId);
```

**Explicit public endpoint**

```csharp
[AllowAnonymous]
[HttpGet("api/public/info")]
public IActionResult Info() => Ok(new { service = "task-api" });
```

## 4. Prohibited practices and anti-patterns

- Storing, returning, or logging plaintext passwords or hashes.
- Roll-your-own cryptography or token formats.
- Trusting a client-supplied owner identifier for authorization.
- Sequential-integer identifiers used as an authorization decision.
- Relying on frontend validation for security.
- `SELECT *` combined with dynamic SQL built from input.
- Wildcard CORS with credentials enabled.
- Committing connection strings, signing keys, or tokens.
- Disabling token validation for convenience, or accepting any issuer.
- Uniform `500` responses that hide a failing authorization check while returning data.
- Seeding "demo" credentials that are actually valid elsewhere.

## 5. Required security tests

The following MUST be covered by automated tests, recorded with observed results:

| Test | Assertion |
| --- | --- |
| Malformed credentials | Requests with a malformed token, empty token, missing header, or bad signature return `401`. |
| Expired credentials | A token past its expiry returns `401`. |
| Authorization bypass | A protected endpoint returns `401` without credentials and does not perform the operation. |
| Cross-user access | User A cannot read, update, or delete User B's record; the response is `403`/`404` and the record is unchanged. |
| Ownership field tampering | Supplying another user's id in the request body does not grant access. |
| SQL injection attempt | A payload in a text field or identifier is stored and read as data and does not alter query semantics. |
| Password secrecy | Registration and login responses contain no password or hash. |
| Duplicate registration | A duplicate email returns `409` and does not create a second user. |

## 6. Verification and review criteria

| Check | Question |
| --- | --- |
| Hashing | Is an established component used, with a unique salt per password? |
| Secrets | Are all secrets outside the repository, with an example file present? |
| Endpoint classification | Is every endpoint explicitly public or protected? |
| Identity source | Does every ownership check use validated claims? |
| SQL | Is every value parameterized? |
| Error leakage | Do error responses avoid internal detail and credential hints? |
| Test evidence | Are the required security tests present with observed results? |
| Evidence hygiene | Do logs and evidence records avoid sensitive data? |
